# How the source is organised

The whole engine is one file, `src/kestrel_4_0.cpp` (about 114,200 lines), plus the 76 MB network that the assembler pulls in with `.incbin "kestrel_net.bin"`. The file is generated from `src/kestrel_4_0_base.cpp` (13,608 lines: the same engine with 8 copies of the search) by `scripts/make_threads.py`: 4,684 lines are Fathom, 107,264 lines are the 128 copies of the search (838 lines each) and about 2,300 lines are everything else (the first 330 lines include the `K41_...` switches of 4.0, set to their final values). To read how the engine works, read the base file; the 4.0 file only has more copies. The line numbers below are for `src/kestrel_4_0.cpp` and only approximate; they are meant as a map, not as a reference.

| Lines | What is there |
|---|---|
| 1 - 331 | includes, platform switches (Windows / Linux / macOS), `KThread`: a `std::thread` replacement with an 8 MB stack (the default stack of musl and macOS threads is too small for a deep search) |
| 332 - 451 | bit tricks, Zobrist keys and attack tables (`initTables`), sliding-piece attacks; with BMI2 the attacks come from PEXT tables (`initPext`), but only on CPUs where PEXT is fast (Intel, AMD Zen 3 and newer), otherwise from the classic tables |
| 452 - 679 | **the network**: the embedded weights and the platform-specific assembler section names, `initNet` / `nnLoadFile` (the `EvalFile` option), `netEval` with an AVX2 path (pairwise product of the two accumulators, a second layer that skips the zero inputs and sums in float32 (an int32 sum could overflow before 2.3), a float tail with FMA) and a plain C++ path with exactly the same results, `featIdx` / `nnBase` (24,576 inputs per side, 32 mirrored king buckets) |
| 680 - 1087 | `Pos`: the board, `make` / `unmake`, move generation, legality, repetition and fifty-move draws, hash keys, and the **accumulators** of the network: they are updated lazily (only for positions that are really evaluated) and king moves use a refresh cache |
| 1088 - 1105 | move printing and `perft` |
| 1106 - 1272 | the old hand-written evaluation of 1.x. It is no longer used in normal play; it stays for `UseNNUE false` and for tests |
| 1273 - 5957 | **Fathom** (new in 3.0), the Syzygy tablebase reader by Ronald de Man, basil00 and Jon Dart (MIT licence; the notice is at the top of the block and in `THIRD_PARTY_NOTICES.txt`). It is the only part of the file that Claude did not write: its source files are pasted in one after the other, inside `namespace fathom`, with the compiler warnings it causes switched off by pragmas. The engine calls `tb_init`, `tb_probe_wdl` and `tb_probe_root_dtz` |
| 5958 - 6020 | the engine side of Syzygy: the options (`SyzygyPath`, `SyzygyProbeDepth`, `Syzygy50MoveRule`, `SyzygyProbeLimit`), `tbProbeWdl`, `tbSetPath`, and `tbRootBans`, which turns the DTZ / WDL ranking of the root moves into the list of moves that are not searched |
| 6021 - 6207 | state shared by all threads: `MAXTH` (128, the number of search copies) and `HASH_MAX_MB`, `depth1Done`, the transposition table (4-entry buckets of two atomic 64-bit words, aged by generation), time limits, `hashMB`, the option variables. New in 3.1: `physMemMB` (installed memory; a `Hash` request above 3/4 of it is cut; on macOS since 3.2) and `zeroMem`, which clears big blocks with several threads; `adviseHuge` (3.2, Linux) asks for transparent huge pages for the table. The switched-off development options (`K31Flags`, `K32Flags`, the `T_...` constants) are declared here |
| 6208 - 113471 | **the search, 128 times**: namespaces `S0` ... `S127`, one per search thread, each a complete copy (own position, history tables, move stacks, killers, correction history). Inside one copy: `evaluate`, SEE (`seeGE`), move ordering (`moveScore`, `quietScore`), `qsearch`, `search` (principal-variation search with null move, reverse futility, ProbCut, internal iterative reduction, late-move reductions and pruning, futility and SEE pruning, singular extensions, tablebase probes at interior nodes), `helperMain` (the iterative deepening of a helper thread, with its own pattern of skipped depths). The copies are identical text; one namespace per thread keeps the thread-private tables out of any shared structure. |
| 113472 - 113490 | glue for the copies (`using namespace S0` for the main thread), the arrays that tie them together (`helperFns`, `nodeCtr`, `clearFns`, `copiesUsed`), node counters (`totalNodes`), and `winFullSpeed`, which asks Windows not to put the engine in "efficiency mode" (EcoQoS) |
| 113491 - 113677 | the experience (position learning) file and the opening book |
| 113678 - 113699 | `go perft` |
| 113700 - 113884 | `think`: the iterative deepening of the main thread, aspiration windows, time management (the soft limit is checked after each iteration, by the smooth rule of 3.2; the hard limit inside the search, but never before depth 1 has completed), MultiPV, book, experience and tablebase lookups at the root, the launcher thread that starts the helper threads (see below), the `info` and `bestmove` output |
| 113885 - 113915 | `accWalk`: the accumulator self-test (every position of a game tree against a rebuild from scratch) |
| 113916 - end | `main`: start-up (tables, network, hash), the command-line modes (`bench`, `acctest`, `perft`, ...), then the UCI command loop with the option parsing |

## Things worth knowing

* **Why 128 copies of the search?** Each thread works on static data of its own namespace, so nothing is shared except the transposition table and the stop flag; no thread-local storage and no pointer to a thread record is needed, and the search code is the code of a single-threaded engine. The price is the size of the file and the memory: every copy reserves about 6.3 MB of address space for its tables (the position with its accumulator ring, the history tables, the pawn table), so the process commits about 0.84 GB when idle although a one-thread game touches only the first copy; compiling the file with g++ takes about two minutes and 1.1 GB. `scripts/make_threads.py` makes the file from `src/kestrel_4_0_base.cpp`: it checks that the 8 copies of the input are identical after renaming, clones the first one up to the requested number, changes the few lines that list the copies and the limits of `Threads` and `Hash`, and checks again that all the copies are identical and that the rest of the file differs from the input only in the places it prints.
* **What 3.1 changes besides the number of copies:** the node limit of `go nodes` and `UCI_LimitStrength` is compared with the node count of the main thread only (`isHelper`; in 3.0 the first helper to reach the limit stopped the search); the helper threads are started by a launcher thread (on Windows at a higher priority, so that with more threads than processors they do not queue behind each other) and the main search begins at once (in 3.0 `think` started the helpers first: 127 threads take 6 - 14 ms with enough processors and 35 - 100 ms and more with fewer processors than threads or a busy computer, which with a short move time was most or all of it); a time limit cannot end a search before depth 1 has completed (`depth1Done`); big hash tables are zeroed by several threads and `ucinewgame` clears only the copies that were started since the last clear; a `Hash` request above 3/4 of the installed memory is cut; the evaluation's pawn table of every copy starts as zeros (a zero entry is the correct entry for a position without pawns) and so no longer takes space in the executable file.
* **Determinism:** with one thread the search is deterministic. The depth-12 `bench` (`kestrel bench 12`) gives the same node count on every platform and for the plain and the AVX2 code (859,322 for 3.0, 3.1 and 3.2, 712,768 for 4.0, whatever the number of copies; the number is recorded in `tests/BENCH` and checked by the GitHub Actions workflow). If you change anything in the search or the evaluation, the number changes; if you only change speed, it must not. With several threads (Lazy SMP) the result differs from run to run.
* **The network is not in git** (76 MB per version). It is a release asset (`kestrel_net_4_0.bin`, the same file as `kestrel_net_3_0.bin`, `kestrel_net_3_1.bin` and `kestrel_net_3_2.bin`), must be saved as `kestrel_net.bin` in the directory where the compiler runs, and can be replaced at run time with `EvalFile`.
* **Syzygy files are not in git either.** With no `SyzygyPath` the engine never touches the tablebase code; see [SYZYGY.md](SYZYGY.md).
* **Search constants** such as the pruning margins sit directly in `search`; in the development builds of 2.2 they are options (`T_...`) for tuning.
