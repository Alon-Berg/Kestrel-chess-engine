Kestrel

A chess engine in one C++17 file. Version 3.1 judges every position with a single 76 MB neural network, reads Syzygy tablebases and searches with up to 128 threads and a hash of up to 1,048,576 MB.

How strong is it?

Kestrel 3.0 against Kestrel 2.3, the packaged x86-64-v3 builds, one thread each, 3,800 games over six time controls (base + increment in seconds). A dot is the measured Elo of 3.0, the bar is the 95 % interval; right of zero means 3.0 is stronger. Kestrel 3.1 plays exactly like 3.0 with one thread, so this is its strength with one thread too.

  • Pooled over all time controls: +130 ± 8 Elo (3,800 games). The gain is largest at the shortest time controls and levels off: from 5 s + 0.1 s per game on it is +104 ± 11 Elo (1,600 games).
  • More threads (3.1): 8 threads score +123 ± 24 Elo against 1 thread of the same build at 10 s + 0.1 s per game (200 games with a development build, a laptop with 22 logical processors) and +108 ± 38 Elo with the release exe (100 games). 64 and 128 threads on those 22 processors gain nothing (+11 ± 71 and +11 ± 57, 32 games each): use at most as many threads as the computer has logical processors. Lazy SMP does not scale linearly (nodes per second 2.9 times higher with 8 threads, 3.7 times with 20), and I could not test a computer with many more processors.
  • The two networks inside the same engine, 20,000 nodes per move: +138 ± 11 Elo for the 3.0 network (2,000 games).
  • The cost of a node is almost the same (1.07 million nodes per second in the depth-12 bench against 1.13 for 2.3), but the search tree is smaller: the bench needs 859,322 nodes instead of 1,051,844 and takes 14 % less time.
  • In my own round robin against 100 other engines (5 s + 0.1 s, one thread) 3.0 scored 76.0 of 200 games; fitted onto the CCRL Blitz scale that is about 3576 (95 % interval 3552 to 3597). An estimate under my own conditions, not a rating-list result.

Use it

  1. Download a file above and unzip it. Keep claude_book.txt next to the engine and switch OwnBook on if you want the opening book (it is off by default; the book file keeps its old name).
  2. In your chess program, add a new UCI engine and point it at kestrel.exe. In Cute Chess this is Tools, Settings, Engines, the plus button.
  3. Set Hash to the memory you can spare (the default is 256 MB) and Threads to the cores you want to use (at most as many as the computer has logical processors; with 64 or more, raise Move Overhead to 50 - 100 ms).

Options include:

  • Hash (up to 1,048,576 MB), Threads (1 to 128)
  • MultiPV, Ponder
  • OwnBook, Experience
  • Move Overhead
  • UCI_LimitStrength, UCI_Elo
  • UCI_Chess960
  • UCI_ShowWDL, UCI_AnalyseMode
  • EvalFile, EvalScale
  • SyzygyPath, SyzygyProbeDepth, Syzygy50MoveRule, SyzygyProbeLimit (new in 3.0)

Syzygy tablebases: set SyzygyPath to the folder with the .rtbw and .rtbz files. The files with 3, 4 and 5 men were tested (940 MB); larger sets use the same code. Without tablebase files nothing changes. Details: docs/SYZYGY.md.

How it works

The search is a conventional alpha-beta search with a transposition table. The evaluation is one network, in five stages; since 3.0 the search also looks positions up in Syzygy tablebases when it has them.

  1. 24,576inputs per side: 12 piece kinds, 64 squares, 32 positions of the own king (mirrored)
  2. 1,536numbers per side, kept up to date move by move instead of recomputed
  3. 768products per side from the two halves of those numbers; about 90 % are zero
  4. 16 → 32 → 1three small layers, one of 8 weight sets chosen by the number of pieces
  5. centipawnsthe score the search uses
  • Training data. 238 million positions of the Lichess evaluation database (CC0), 2.36 billion positions along the best lines stored with its entries, and 6.6 million positions from Kestrel's own games, all labelled by Stockfish evaluations: about nine times as many as 2.x. The 2.x network overfitted the database positions alone; the positions along the lines removed that limit.
  • Speed. A network this size costs time, so the evaluation code skips the zero inputs, builds the per-side numbers only for positions that are really evaluated, keeps a refresh cache for king moves and loads the weights ahead of time. Together that made the engine 1.95 times faster than its first version with identical moves and scores.
  • Threads. Lazy SMP: every thread searches the same position with its own tables and shares only the transposition table. The search code exists once per thread (128 copies of one section of the file, made from the 3.0 source by a script that checks that they are identical), so a thread needs no pointer to a record of its own.
  • The network. 39.1 million parameters, trained from scratch in two stages (54 and 8 hours) on the CPU of one laptop, with no GPU. On held-out positions its error is 17 % lower than the 2.3 network's on Lichess positions and 32 % lower on positions from Kestrel's own games.

Build it yourself

The source is one file, src/kestrel_3_1.cpp. The 76 MB network is not stored in git: download kestrel_net_3_1.bin from the release, save it as kestrel_net.bin in the folder where you run the compiler, and compile.

g++ -std=c++17 -O3 -march=x86-64-v3 -static -pthread -DNDEBUG -o kestrel.exe src/kestrel_3_1.cpp

The source has 128 copies of the search: compiling it takes about two minutes and 1.1 GB of memory. Other CPUs and operating systems: docs/BUILDING.md.
