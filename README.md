# Kestrel

[![verify-release](https://github.com/Alon-Berg/Kestrel-chess-engine/actions/workflows/verify-release.yml/badge.svg)](https://github.com/Alon-Berg/Kestrel-chess-engine/actions/workflows/verify-release.yml)

A UCI chess engine in one C++17 file, written by [Claude](https://www.anthropic.com/claude), an AI model made by Anthropic, with one exception: the Syzygy tablebase reader inside it is [Fathom](https://github.com/jdart1/Fathom) (MIT licence, see [THIRD_PARTY_NOTICES.txt](THIRD_PARTY_NOTICES.txt)). Since version 2.0 it judges every position with one large neural network (39.1 million parameters) that is stored inside the executable.

**[Download the latest release](https://github.com/Alon-Berg/Kestrel-chess-engine/releases/latest)** (Windows, Linux, macOS) · [Web page](https://alon-berg.github.io/Kestrel-chess-engine/) · [Play in the browser](https://alon-berg.github.io/Kestrel-chess-engine/play/) · [Changelog](CHANGELOG.md) · [UCI options](docs/OPTIONS.md) · [Syzygy tablebases](docs/SYZYGY.md) · licence MIT

## Strength

All numbers are my own, from fastchess matches on one laptop (1 thread, 64 MB hash, no book, no learning, no adjudication, the same openings for both sides, every engine process at full speed with Windows' efficiency throttling switched off). No rating list has tested Kestrel yet. Elo is Kestrel 3.0 against the older version, with fastchess's 95 % interval. Kestrel 3.1 has the network and the search of 3.0 and plays exactly like it with one thread, and 3.2 plays like 3.1 except for the time management of searches with a clock, so the numbers below hold for 3.1 and 3.2 with one thread. Kestrel 4.0 has the same network and a faster, changed search: its numbers are in the paragraph 'Speed and search (4.0)' below. Kestrel 4.1 plays exactly like 4.0 with one thread (a bug-fix release), so those numbers hold for 4.1. Kestrel 4.2 has the same network in a half-size form, a faster evaluation and one more search change: its numbers are in the paragraph 'Speed (4.2)' below. Kestrel 5.0 uses more of the clock, has a retuned search and a network trained further: its numbers are in the paragraph 'Clock, search and network (5.0)' below.

| Time per game (base + increment, seconds) | Kestrel 3.0 against Kestrel 2.3 |
|---|---|
| 1 + 0.01 | +192 ± 23 |
| 2 + 0.02 | +150 ± 23 |
| 3 + 0.03 | +146 ± 17 |
| 5 + 0.1 | +105 ± 14 |
| 10 + 0.1 | +102 ± 22 |
| 20 + 0.5 | +102 ± 28 |

Pooled over all time controls: **+130 ± 8 Elo** against 2.3 (3,800 games, inverse-variance weights). The gain is largest at the shortest time controls and levels off with more time: from 5 s + 0.1 s per game on it is **+104 ± 11 Elo** (1,600 games). The gain comes from the network alone: the search and the time management are those of 2.3, and in a match of the two networks inside the same engine at 20,000 nodes per move the 3.0 network is +138 ± 11 Elo ahead (2,000 games). The network has the same size as before, so the cost of one node is almost the same (1.07 million nodes per second in the depth-12 bench on a performance core against 1.13 million for 2.3, 5 % fewer), but the stronger network makes the search tree smaller: the bench needs 859,322 nodes instead of 1,051,844 and takes about 808 ms instead of 935 ms (14 % less time).

In my own round robin against 100 other engines (5 s + 0.1 s per game, one thread, this laptop, every engine at full speed) 3.0 scored 76.0 of 200 games; fitted onto the CCRL Blitz scale through the engines whose ratings did not change that is about 3576 (95 % bootstrap interval 3552 to 3597), which would put it 71 of 101 in that table. This is an estimate under my own conditions, not a rating-list result.
Raw results: `logs/fast_matches_3_0.txt`.

**Many threads (3.1):** 8 threads score +123 ± 24 Elo against 1 thread of the same build at 10 s + 0.1 s per game (200 games with a development build; +108 ± 38 in 100 games with the release exe; on a laptop with 22 logical processors). 64 and 128 threads on the same 22 processors gain nothing (+11 ± 71 and +11 ± 57, 32 games each), so use at most as many threads as the computer has logical processors. Lazy SMP does not scale linearly (the nodes per second grow 2.9 times with 8 threads and 3.7 times with 20 on that laptop), and I could not test a computer with many more processors; details in [CHANGELOG.md](CHANGELOG.md).

**Time management (3.2):** a smoother rule for when to stop searching, in games with a clock: Kestrel 3.2 against 3.1 scored +11.2 ± 6.2 Elo at 3 s + 0.03 s per game (4,000 games) and +6.2 ± 7.5 at 5 s + 0.1 s (2,000 games), packaged builds, one thread; together +9.2 ± 4.8 Elo (6,000 games). No change at all with a fixed move time, depth or node limit. Raw results: `logs/fast_matches_3_2.txt`.

**Speed and search (4.0):** Kestrel 4.0 against 3.2 scored +31.9 ± 5.8 Elo at 3 s + 0.03 s per game (4,000 games) and +26.8 ± 7.1 at 5 s + 0.1 s (2,000 games), packaged builds, one thread; together +29.9 ± 4.5 Elo (6,000 games). The network is the one of 3.0 - 3.2: the gain comes from a search that makes 10 % more nodes per second (the depth-12 bench takes 24 % less time) at the same strength per node, and from two changes to the move ordering (+22.9 ± 6.1 Elo at 20,000 nodes per move). Raw results: `logs/fast_matches_4_0.txt`.

**Speed (4.2):** Kestrel 4.2 against 4.1 scored +10.2 ± 5.8 Elo at 3 s + 0.03 s per game (4,000 games) and +1.7 ± 7.0 at 5 s + 0.1 s (2,000 games), packaged builds, one thread; together +6.7 ± 4.5 Elo (6,000 games) (2,706 further games were dropped and replayed because other programs loaded the laptop while they were played; the raw match results and the rule are in `logs/fast_matches_4_2.txt`). The network of 3.0 - 4.1 is stored in a smaller form: the 24,576 x 1,536 first-layer weights are stored as 8-bit integers with one integer scale per neuron (the weight of neuron j is row[j] x K[j], K between 1 and 127, K = ceil(max |w| / 127) over all rows, so nothing is clipped) instead of 16-bit integers: the network file is 38.6 MB instead of 76 MB and the Windows x86-64-v3 exe about 44 MB instead of 82 MB. Rounding the weights costs about 0.5 % of the held-out error of the network; the three output layers (16 -> 32 -> 1, 8 buckets) were then fitted again to the output of the original network for 3,000 steps with the first layer fixed (mean difference to the original network's output on 150,000 held-out positions: 4.1 cp instead of 4.6 cp with the rounded weights). Without that fit the rounded network was -7.1 ± 8.6 Elo against the 16-bit network at 20,000 nodes per move (2,000 games); the result against 4.1 above is for the final build with the fit. The evaluation is faster: the accumulator update uses `vpmaddubsw` (it widens, scales and adds two rows in one instruction) on rows that the new network file `KSTRNET4` stores in a permuted order, so that the AVX2 code reads the file in place; the second layer adds the products of four input pairs as 32-bit integers before it converts them to float (a check at load time makes sure that no sum can overflow, otherwise the old path runs), and the third layer uses two independent chains of fused multiply-adds. The depth-12 bench takes 8 % less time (500 ms against 546 ms, median of 15 alternating runs on one core) for a tree that is 7 % smaller (662,820 nodes against 712,768); in the release matches (games with a clock) the mean search depth of 4.2 is about 0.1 plies greater than that of 4.1, at 3 s + 0.03 s and at 5 s + 0.1 s. The correction history of the search also uses the previous move: the correction of the static evaluation also uses the previous move (`K32Flags` 12 = 4 + 8; 4.1: 8): +4.9 ± 4.3 Elo at 20,000 nodes per move in four matches of 2,000 games (+10.9, +1.0, +7.6 and +0.0). Raw results: `logs/fast_matches_4_2.txt`.

**Clock, search and network (5.0):** Kestrel 5.0 against 4.2 scored +45.5 ± 5.1 Elo at 3 s + 0.03 s per game (4,000 games) and +42.0 ± 5.0 at 5 s + 0.1 s (3,820 games), packaged builds, one thread; together +43.7 ± 3.6 Elo (7,820 games) (180 further games were dropped, not replayed, because other programs loaded the laptop while they were played; the same match with all its games gives +39.2 ± 5.1 at 5 s + 0.1 s (4,000 games); the raw match results and the rule are in `logs/fast_matches_5_0.txt`). The clock: 4.2 ended its games with about 28 % (5 s + 0.1 s per game) and 19 % (3 s + 0.03 s) of the time budget (the base time plus the increments earned) still on the clock (on average 3.0 s of the 5 s and 0.88 s of the 3 s): its rule spent about one increment per move in the long run. 5.0 counts the increments still to come in the planned time of a move, (time left + 40 increments) / 28 + 0.75 increment (28 moves to go unless the GUI sends `movestogo`; 4.2: time left / 28 + 0.75 increment), and reads the clock every 256 nodes instead of every 2,048 (at a low clock the hard limit was overshot by several milliseconds). The rule for stopping after an iteration is that of 3.2. With only this change, in the same build against the 4.2 rule: +12.9 ± 8.9 Elo at 3 s + 0.03 s and +17.4 ± 8.5 at 5 s + 0.1 s (1,400 games each); together +15.1 ± 6.1 Elo. In the gate games against 4.2 the new rule ended its games with about 10 % (5 s + 0.1 s) and 14 % (3 s + 0.03 s) left. The default of `Move Overhead` is now 10 ms (4.2: 5 ms), because 5.0 plays closer to the clock. The search: the reduction of a late quiet move is computed in hundredths of a ply and rounded at the end (`K31Flags` 4: a table of depth and move number; less in principal-variation nodes, more when the position is not improving and at expected cut nodes, less for checks and killer moves, minus the history score). Three ideas known from Stockfish were added in Kestrel's own code (bits of `T_K50F`, 23 = 1 + 2 + 4 + 16): the depth is adjusted in hindsight after a reduced move (bit 1: +4.6 ± 5.7 Elo at 20,000 nodes per move, 8,000 games), the reduction is one ply more when many moves below the node caused beta cutoffs (bit 2: +5.2 ± 5.7), and the depth of the aspiration search at the root is lowered by the number of fail highs so far in the iteration (bit 4: +4.2 ± 5.7); bit 16 keeps the result of an iteration that the clock cuts off when a root move had already improved alpha (+2.1 ± 1.7 in 6,000 games on a virtual clock). Three switches of 4.0 / 4.1 were turned on: `K41_QTT` (the stand-pat value of the quiescence search is improved by the bound of the hash entry), `K41_PRX` (checking moves are exempt from futility, history and SEE pruning) and `K41_ORD` 2 (the move ordering rewards leaving a square that a cheaper enemy piece attacks and punishes entering one in proportion to the value of the piece, instead of by a constant); together +6.4 Elo at 20,000 nodes per move (8,000 games). 25 search constants (margins, reduction terms, history and ordering weights) were tuned by SPSA (684 iterations, 323,456 games at 15,000 nodes per move); their values are the `KVAR` constants of `src/kestrel_5_0_base.cpp`. The network is the network of 3.0 trained further (see 'How the network was made'): +3.8 ± 4.3 Elo against the network of 4.2 in the same engine at 20,000 nodes per move (8,000 games). The speed: the depth-12 bench takes 43 % less time than that of 4.2 (279 ms against 491 ms, median of 9 alternating runs on one core): 407,653 nodes against 662,820, with about 8 % more nodes per second. Raw results: `logs/fast_matches_5_0.txt`.

For comparison, Kestrel 2.0 against the older versions (the same kind of match): **+37 ± 11 Elo** against 1.1 (1,900 games) and **+48 ± 13** against 1.0 (1,500 games), see `logs/fast_matches_2_0.txt`.

## What is inside

* **Evaluation:** one network. 24,576 inputs per side (12 piece kinds × 64 squares × 32 horizontally mirrored king buckets), 1,536 integer accumulators per side kept up to date move by move, a pairwise-product activation, then 16 → 32 → 1 neurons with 8 output buckets chosen by the number of pieces. The second layer skips the zero inputs (about 90 % are zero). Since 4.2 the 24,576 x 1,536 first-layer weights are 8-bit integers with one integer scale per neuron (the network file is 38.6 MB, before 76 MB). An AVX2 code path does the work on CPUs that have it, with exactly the same results as the plain code (the same bench node count and the same evaluation of 2,000 test positions).
* **Search:** iterative deepening with aspiration windows and principal-variation search; a bucketed transposition table; null-move pruning, reverse futility, ProbCut, internal iterative reduction, late-move reductions and pruning, futility and SEE pruning, singular extensions; killer, counter-move, history and continuation-history move ordering; a correction history for the static evaluation; quiescence search with SEE; Lazy SMP with up to 128 threads (3.1; 3.0: 8) and a hash of up to 1,048,576 MB (3.0: 4096); a smooth time management (3.2) that since 5.0 counts the increments still to come; late-move reductions in hundredths of a ply with a cutoff-count term and a hindsight depth adjustment (5.0); Stockfish's repetition rule and a damping of the evaluation near the fifty-move limit.
* **Syzygy tablebases** (new in 3.0): probing inside the search and at the root with the WDL and DTZ files; the 3-4-5-men files were tested, 6 and 7 men use the same code. See [docs/SYZYGY.md](docs/SYZYGY.md).
* **Features:** Chess960, `MultiPV` (up to 8), `UCI_ShowWDL`, `UCI_AnalyseMode`, `UCI_LimitStrength`, `go movetime` with `Move Overhead`, pondering, an optional opening book and an optional "experience" file (position learning), `EvalFile` to load another network of the same format.
* **Not available:** NUMA awareness and Windows large pages (since 3.2 the hash table is advised to use transparent huge pages on Linux).

## Use it

Unzip a release file and add `kestrel.exe` (or `kestrel`) to a UCI program such as Cute Chess, Arena, En Croissant or Lucas Chess. The x86-64-v3 builds need a CPU with AVX2 and BMI2 (most PCs since 2015); the v2 and generic builds work on older CPUs and are about 74 % slower (5.0, bench of depth 12 on one core: their plain C++ evaluation does not use the AVX2 kernels). The defaults are `Hash` 256 MB, 1 thread, `Move Overhead` 10 ms (since 5.0), opening book and learning off; all options are in [docs/OPTIONS.md](docs/OPTIONS.md). The exe is about 44 MB because the network is inside it, and it is not code-signed (some virus scanners distrust big unsigned programs); the SHA-256 of every release file is in `SHA256.txt` on the release page.

## Build

The 38.6 MB network is not stored in git. Download `kestrel_net_5_0.bin` from the [release page](https://github.com/Alon-Berg/Kestrel-chess-engine/releases/latest), save it as `kestrel_net.bin` in the folder where you run the compiler (the assembler looks for it in the **current directory**) and compile:

```
g++ -std=c++17 -O3 -march=x86-64-v3 -static -pthread -DNDEBUG -o kestrel path/to/src/kestrel_5_0.cpp
```

The source has 128 copies of the search, so the compile takes about 6 minutes and 1.2 GB of memory (4.2: about 5.1 minutes, 4.1: about 2.6 minutes, 3.0: 16 s). Other CPUs (x86-64-v2, plain x86-64), Linux, macOS and ARM: [docs/BUILDING.md](docs/BUILDING.md). `kestrel bench 12` must print `bench: nodes 407653`.

## How it was tested

* Two black-box audits of the UCI protocol and the rules (83 + 31 checks, `tests/audit_probe.py`, `tests/audit_sem.py`; python-chess is the rules oracle for the second one).
* A 30-check verification with GCC and with clang AddressSanitizer + UBSan builds (also with 4 threads): accumulator self-test over 186,000 positions, perft, perft against python-chess, evaluation mirror symmetry, PV legality, UCI fuzzers, `go infinite` / `stop` races, MultiPV and ponder checks, and for 3.0 the Syzygy test (`tests/tb_test.py`: win/draw/loss of random 3-5-men positions against python-chess reading the same files, the root move filter, search, and conversion of won endgames). Logs are in `logs/`.
* The Windows x86-64-v3 build ran all of this (for 5.0 without the clang AddressSanitizer + UBSan builds: clang was no longer installed on the laptop, the workflow ran them on GitHub's Linux machine and they passed). The repository's GitHub Actions workflow ([`verify-release.yml`](.github/workflows/verify-release.yml)) runs the published files on GitHub's machines (Linux x86-64 v3, v2 and generic, Linux ARM64, macOS Apple silicon, Windows): its runs on the published files are on the Actions page; the first run on the 5.0 files passed all 15 jobs, and the depth-12 bench is 407,653 nodes on every platform.
* The macOS Intel build is run by the same workflow on GitHub's macOS Intel machine (`macos-15-intel`); I have no Mac myself.
* For the many threads of 3.1: thread start / stop stress tests with 16, 64 and 128 threads, `tests/breakers.py` with 1, 8 and 64 threads, an AddressSanitizer + UBSan build run with up to 128 threads, matches of 8 threads against 1 (200 and 100 games), and the scaling measurements of the changelog (`logs/threads_3_1.txt`). All of it ran on one Windows laptop with 22 logical processors. For 3.2 the same suites ran on the 3.2 files (`logs/threads_3_2.txt`, `logs/repo_tests_3_2.txt`), for 4.0 on the 4.0 files (`logs/threads_4_0.txt`, `logs/repo_tests_4_0.txt`), for 4.1 on the 4.1 files (`logs/threads_4_1.txt`, `logs/repo_tests_4_1.txt`), for 4.2 on the 4.2 files (`logs/threads_4_2.txt`, `logs/repo_tests_4_2.txt`), for 5.0 on the 5.0 files (`logs/threads_5_0.txt`, `logs/repo_tests_5_0.txt`).

## How the network was made

The network of 3.0 has the shape of the 2.x network (39.1 million parameters, 24,576 inputs per side, 1,536 neurons, 16 -> 32 -> 1, 8 output buckets) and was trained again from scratch with a longer run and about nine times more positions. All training ran on the CPU of one laptop (Core Ultra 7 155H, no GPU) with my own trainer (not in the repository): Adam, batches of 16,384 positions, a cosine learning-rate schedule. The loss is the squared difference between the network's win probability and the target, which is the win probability of the Stockfish evaluation, `1 / (1 + 10^(-cp / 400))` (mixed 80:20 with the game result for positions that have one). Stockfish only supplied labels; none of its code is in Kestrel.

Three sources of positions, all quiet (side to move not in check, best move not a capture):

* **238 million positions of the Lichess evaluation database** (CC0): the deepest evaluation of each position, depth 20 or more, a centipawn score (no mate), at most 1,500 centipawns. These are all the positions the database offers in that form, and they are everything the 2.x network learned from (plus 12 million positions of Kestrel's own games). Training on them for longer only overfitted: after about 50 hours the error on held-out positions stopped falling while the error on the training positions kept falling.
* **2.36 billion positions along the best lines** stored with every entry of that database (the lines that Stockfish found): the positions after 1 to 9 moves of the best line and after 1 to 6 moves of up to four other lines, each labelled with the evaluation of its line, with every duplicate and every position of the held-out set removed. They are new positions with high-quality labels, and they cut the held-out error of a small test network by about a quarter. They were mined in two batches that do not overlap: 1.08 billion for the main run and 1.28 billion for the second stage.
* **6.6 million positions from self-play games of Kestrel and its predecessor engines**, labelled by Stockfish at depth 10: positions of the kind the engine really meets in a game.

Training had two stages. The main run took 650,000 steps (54 hours) with a learning rate that fell from 1e-3 to 1e-5; every batch took 56 % of its positions from the first batch of line positions (each seen about 5.5 times), 3 % from Kestrel's own games and the rest from the database positions (each seen about 18 times). The second stage continued from the final network of the main run for 90,000 steps (8 hours) with a learning rate that fell from 6e-5 to 6e-7; 70 % of every batch came from the second set of line positions, which the main run had never seen and which were used at most once. The shipped network is the best snapshot of the second stage by held-out error. It beat the best snapshot of the main run by +7.7 ± 8.1 Elo in 4,000 equal-node games, and the main run's network beat the 2.3 network by +129.8 ± 10.9 Elo in 2,000 equal-node games (20,000 nodes per move).

The held-out error (mean squared error of the win probability, 400,000 positions of the database that were never trained on, and 150,000 of Kestrel's own games) fell from 0.0128 / 0.0164 for the 2.x network to 0.0107 / 0.0111 (17 % and 32 % lower). Two earlier ideas did not help and are not in 3.0: fine-tuning on fresh games of the engine itself labelled by Stockfish (-6.7 ± 11.2 Elo against the network it started from), and training longer on the database positions alone.

The network of 4.2 is the network of 3.0 - 4.1 in a smaller form, not a new network: the first-layer weights were rounded to 8-bit integers with one integer scale per neuron (K = ceil(max |w| / 127), the largest value of a neuron maps to at most 127, nothing is clipped; held-out error +0.5 %), and then only the three output layers were trained again for 3,000 steps against the output of the original network, with the first layer fixed (distillation: the target is the original network's win probability, not Stockfish's, and not the game result). Training the first layer too (fake-quantised weights, 24,000 steps with the original labels) did not recover the rounding: the network drifted away on positions of real games. The tools that made the file are not part of this repository.

The network of 5.0 is not a new one: it is the network of 3.0 - 4.2 trained further, in the same format as 4.2: two fine-tuning runs of 24,000 steps (batches of 16,384 positions) from the final state of the 3.0 training, on the original positions plus 4.08 million positions from Kestrel's own games labelled by Stockfish at depth 10 (20 % of every batch in one run, 7 % in the other); the weights are the average of the last three snapshots of each run (and the two averages are averaged again), rounded to 8-bit integers with one integer scale per neuron as for 4.2 (`KSTRNET4`, 38.6 MB; the output layers were not fitted again this time). At 20,000 nodes per move the 8-bit network scored +3.8 ± 4.3 Elo against the network of 4.2 in the same engine (8,000 games; the 32-bit network before the rounding: +6.1 ± 5.0, 6,000 games). The tools that made the file are not part of this repository.

## Versions

5.0 (more of the clock is used, a retuned search and a network trained further; +43.7 ± 3.6 Elo against 4.2), 4.2 (the network in a half-size form and a faster evaluation; +6.7 ± 4.5 Elo against 4.1), 4.1 (bug fixes: malformed FEN strings, small node limits and UCI_Elo; plays like 4.0 at full strength), 4.0 (a faster search and two changes to the move ordering; +29.9 ± 4.5 Elo against 3.2), 3.2 (smoother time management; huge-page advice for the hash table on Linux), 3.1 (up to 128 threads and a hash of up to 1,048,576 MB; plays like 3.0 with one thread), 3.0 (a new network trained on about nine times more positions, Syzygy tablebases), 2.3 (bug fixes: an evaluation overflow in endgames; obsolete options with wrong defaults removed, which was 2.2), 2.1 (default settings for chess-engine testers), 2.0 (the large network), 1.1 and 1.0 (two small networks and a hand-written evaluation): see [CHANGELOG.md](CHANGELOG.md). What the README said about 1.x is kept in [docs/KESTREL_1_x.md](docs/KESTREL_1_x.md).

## Layout

* `src/kestrel_5_0.cpp` the whole engine (6.5 MB: the engine with 128 copies of the search, made by `scripts/make_threads.py` from `src/kestrel_5_0_base.cpp`, which is the same engine with 8 copies and the file to read); `src/kestrel_4_2.cpp` is 4.2 (from `src/kestrel_4_2_base.cpp`), `src/kestrel_4_1.cpp` is 4.1 (from `src/kestrel_4_1_base.cpp`), `src/kestrel_4_0.cpp` is 4.0 (from `src/kestrel_4_0_base.cpp`), `src/kestrel_3_2.cpp` is 3.2 (from `src/kestrel_3_2_base.cpp`), `src/kestrel_3_1.cpp` is 3.1 (made from `src/kestrel_3_0.cpp`, which is 3.0); `src/kestrel_2_0.cpp` is 2.0 - 2.3; `src/kestrel_1_1.cpp` and its network headers: Kestrel 1.1; `src/claude_book.txt` the optional opening book (the file keeps its old name)
* `scripts/` the generator of the 3.1, 3.2, 4.0, 4.1, 4.2 and 5.0 sources (`make_threads.py`) and the Windows version-info file (`kestrel.rc`)
* `docs/` build notes, option reference, Syzygy notes, an architecture guide, release notes of 1.x, the web page (`index.html`)
* `logs/` result and test logs of the releases
* `tests/` black-box test scripts for any Kestrel executable (see `tests/README.md`)

The tools that train the network and run the long test suites are not part of this repository.
